We do not stop to think before every action. We can walk while planning a route,
carry on a conversation while making coffee, or adjust a movement before putting the
change into words. Different forms of control work together: deliberate thought helps
us choose a direction, the cerebellum helps coordinate movement, and reflexes provide
rapid responses without waiting for conscious deliberation. These processes overlap,
rather than taking turns at every step.

Experience changes how we act, too. A task that once demanded close attention can
become a familiar skill. We learn from an attempt, carry useful adjustments into the
next one, and return to deliberate thought when the situation calls for it. Thinking,
acting, responding and learning are parts of an ongoing activity.

**We want future agents to be Automatic Control systems:** able to turn goals into
action, judge when to continue or reconsider, and coordinate tools, policies and other
agents as the task demands. They should notice when results drift from intent, adjust
their approach, and turn experience into reusable skills—while remaining receptive to
your direction throughout the work.

**The Harness is our step toward that future.** Models reason and write programs;
programs and learned policies act; reactive rules respond as conditions change.
Execution can overlap the next decision, and tested learning can become usable within
the same run, across the environments and capabilities you connect.

## Runs continuously

**The system keeps sensing and acting without pausing for every decision.** In a
changing environment, things keep happening while the model thinks. The Harness keeps
the control process running: programs continue their work, reactive rules check the
changes they watch for, and the model considers what comes next when needed.

Different changes can be handled at different levels. A program can use a result to
continue an existing procedure, and configured reactive rules can respond promptly to
familiar conditions. Problems beyond those mechanisms reach the model for a fresh
judgment. The time spent thinking need not become a delay in the whole system's
response to its environment.

That continuity extends between programs. Rules stay active after one program finishes
and before the next begins.
Actions can continue, pending operations can wait, and stop conditions can interrupt
execution. Continuous operation keeps these processes connected while preserving the
ability to reconsider and respond to your direction.

## One call, many actions

A model call produces a program for a piece of work. That program can compose tools
and skills, inspect results and choose what to do next within the procedure it has
written.

Programs can use **learned policies** as well as code. A program hands a motion to a
policy for a bounded execution, then checks the result before continuing. Observations
and actions are translated by the environment's adapter; completion and interruption
follow the same execution lifecycle as other skills.

The model returns at **decision points**: when the task starts, a program ends, you
send a message, or an event requires a new judgment. It reads the reported results and
unresolved events before deciding how to proceed. This keeps a decision useful for as
long as the running code can handle the situation, while leaving room to reconsider.

## Thinking while acting

Carrying out one decision and preparing another can happen together. During a long
program, the model can prepare a follow-up once, with a condition for when it applies.
When the program finishes, the reply is used only if that condition is met and its
relevant inputs still hold. A result that differs from the expectation needs to be
considered on its own terms.

Independent programs and reactive rules can continue during a model call. A guard can
respond to a known condition without waiting for a reply; an unresolved event or a
message from you can prompt a fresh decision. The timeline shows the overlap between
thinking and execution. [Watch and replay a run](/docs/use/replay/)

## Learning while working

With learning enabled, the agent can turn experience into something it can use again:
notes and memories to consult, skills to run, and reactive rules to respond to familiar
conditions. These live in an explicitly bound **library**. The model's weights do not
change.

Executable additions are tested and admitted before activation. An accepted revision
can become available between programs in the same run, so a checked procedure can help
with the rest of the task. Recording an observation, verifying a skill and showing
that it improves task results are different steps; a library retains their evidence.

The agent can explore an environment before taking on a task, or propose additions as
it works. A frozen library lets later runs use the same experience without changing it.

## Four layers

The Harness organizes control around four responsibilities. They work at different
cadences, so a model's deliberation need not set the pace of every action or response.

<HarnessFigure label="The four layers of The Harness: language model, programs and learned policies, reactive layer, and safety layer." />

| Layer | Runs | What it does |
|---|---|---|
| Language model | at decision points | interprets observations and results, plans, writes programs and responds to you |
| Programs and learned policies | while a program runs | compose skills and tools or invoke a learned policy; each skill call runs as a bounded execution ending in completion or interruption |
| Reactive layer | when what a rule reads changes, or on time | judges rules and event handlers, which start a program, end an execution or raise an event without calling the model |
| Safety layer | before commands execute | checks commands at the worker boundary, whether they come from programs, policies or reactive rules; learned rules cannot rewrite these constraints |

**The tick coordinates these layers; it is not a fifth layer.** It advances executions, checks reactive rules and handles interruptions independently of model calls.

The tick exists while an execution or a rule on time needs it, and not otherwise: a task
that sets no rule on time is driven by events alone. An environment says how fast it can
be driven; continuous control follows the rules a task has set;
it does not mean repeatedly calling the model or issuing actions when no work is needed.

The worker runs the
environment and enforces safety at the execution boundary.

These are responsibilities, not four processes or a sequence of four stages. An event
can move a problem to the level that can handle it: a guard ends an execution, its
program handles the event, or the unresolved event reaches the model at a decision
point.

## Works with what you already use

The Harness connects in both directions: other tools can call it, and its programs
can use other tools. These connections make different combinations possible without
tying the control structure to one model, application or environment.

| Connection | How it fits |
|---|---|
| Apps | An MCP client such as OpenCode, Cursor or Codex can give The Harness a task and follow its session; ACP editors can use it from their agent panel. |
| Environments | Packages provide observations, commands, workers, skills and prompts for a desktop, browser, project workspace, game or robot. |
| Models | A configured hosted provider or a model service you run supplies the model decisions. |
| MCP servers | Programs use the tools of a connected server, such as agent-desktop or your own service, under explicit grants. |
| Agents | Another agent can drive The Harness through MCP, or run inside a hosted session through a supported terminal or ACP adapter. |
| Learned policies | Programs hand bounded executions to a policy through its adapter and inspect the results. |

An external agent keeps its own decision process; hosting it does not turn its internals
into The Harness's four layers. The session provides a place to follow the work and
send direction. Agent Skills add instructions that the model can consult when needed.

Packages install on demand by default for the task or capability you select. Installing
core does not choose unrelated external apps or agents for you.
[Connect The Harness to other tools](/docs/extend/integrations/)

## You stay in the loop

A task remains open to your direction while it runs. Add context or change a requirement,
and the model considers what should continue, finish or stop. You can follow the timeline,
review programs before execution, or pause and take over in supported computer workspaces.
The available approvals and takeover behavior depend on the workspace and its settings.
[Interrupt and take over](/docs/use/interrupt/)

The core carries out bounded tasks with their own context, budget and execution record.
A program finishing is evidence to inspect, not by itself proof that the goal was met.
The optional agent package adds identity, multi-turn conversation and personal memory
across tasks; the core can run and learn without it. This lets you keep the conversation
where you want it and bring The Harness in for the work.
