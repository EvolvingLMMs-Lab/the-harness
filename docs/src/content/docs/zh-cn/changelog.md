首个公开快照正在准备中。公开版本的变更将在这里记录。

## 0.80.2（尚未发布）

终端对话在对话打开时（启动时和 `/new` 之后）、输入第一条消息之前就询问在哪里工作；高亮上一次的选择，回车即确认。0.80.0 里这个询问要等第一条消息发出后才打开，而发送消息的那次回车会立刻确认高亮的选项，所以看不到选择。开场的选择被关掉后、消息发出时仍会打开的选择，在打开后的 0.6 秒内不接受回车。第一条消息之前，状态栏显示已选的环境。不用环境的对话不再打印评测器一行；browser 包可以和 computer 0.7 一起安装（browser 0.5.1）。检查：环境选择的 15 项专项测试通过，其中一项通过管道送入残留的回车；终端对话本身没有做实机操作。

## 0.80.1（尚未发布）

普通对话回答只显示一次。对应的 `agent_message` 通知现在标明已有的模型回答，共享 transcript 只展示原回答，原始 trace 和收件箱仍保留通知。独立消息、不同轮次的相同回答，以及模型和程序的结束输出保持正常。专项回归贯通运行时事件、终端渲染和 trace 回放，修复前复现重复，修复后覆盖上述边界；未运行全量测试或真实模型评测。

## 0.80.0（尚未发布）

对话的环境不再由一项保存的设置决定，观测也不再是每种环境固定的一套。

- **每个对话选择在哪里工作。** 选项来自已安装的包：不用环境（只对话：没有工作进程，没有画面）、项目文件夹、后台浏览器、后台应用、你的桌面、独立显示环境。`session.environment` 可取 `ask`（默认：每个新对话都问，高亮上一次的选择）、`last` 或某一种环境。`computer.mode` 现在是首先高亮的电脑环境，已保存的值继续生效。终端有开场选择和 `/environment`，app 的输入框多了两个选项，命令行接受 `--workspace none|project|...`，Python 接受 `workspace="none"`。没有人可问而设置为 `ask` 时，任务不会启动，错误信息会指出该用哪个参数。
- **一个 agent 在需要时取用别的环境。** `use_environment(kind, why)` 把它接入同一个对话，`release_environment(kind)` 归还；它的调用带环境名（`desktop.click(...)`、`project.run_command(...)`、`browser.read_page()`）。`environments.attach` 对许可分级（`never`、`ask_each`、`ask_once_session`、`allow`，默认 `ask_once_session`），可按环境设规则。询问里显示模型给出的理由。`physical.level = "allow"` 时不询问；`never` 仍然拒绝；没有人可问而级别要求询问时，拒绝并说明原因。每次取用及其理由都出现在对话、时间轴和 trace 里。真实鼠标键盘仍受真实键鼠策略约束。
- **子 agent 默认关闭。** 用 `session.agents`、`--agents`、`/agents`、app 里的开关或 `runtime={"agents": True}` 打开，或者 agent 用 `request_agents(why)` 提出、你同意后打开。
- **模型需要时才看。** 每一轮都是文本。`look()` 把画面连同该程序的结果放进下一轮，`watch()` 让每个程序（或每隔几秒）都带上画面直到 `unwatch()`，一张图默认只保留一次回复，除非模型保留或钉住它。声明了 `runtime.cameras` 的配置保持原有的持续画面：解析后的评测 agent 在机器人、桌面和游戏三张表上与 0.79.2 逐字节一致，机器人相关的包没有改动。
- **不能读图的模型。** 模型条目记录这一点（provider 目录给出时采用，可修改）。这样的模型不会收到图；`model.vision` 指定为它描述画面的模型；选择环境时，有屏幕的环境旁边会注明。
- **验证器**拿到状态、环境报告的元素或页面文本，以及画面。

在 Windows、Python 3.14 上检查：针对改动契约的 75 项专项测试通过（环境选择 13、取用环境与子 agent 22、画面与模型标记 17、首次选择 14、工作区提供方 7、模型归属 2）；文档类型检查、构建（121 页）和体积预算通过。用 DeepSeek V4.1 Flash 经 Python 接口和命令行跑了真实任务：不用环境时 0 个工作进程、0 张图，1 次模型调用作答；项目任务修改样式表后带理由询问一次取用后台浏览器，同意后在同一对话里完成（26 次模型调用，3 张图，全部来自它自己的查看）；拒绝后不用浏览器继续完成（12 次调用，0 张图）；桌面任务从窗口元素读出表格单元格（1745），3 次调用、1 张图（来自它自己的查看）；把模型标记为不能读图后，项目任务 0 张图完成，桌面上查看也发送 0 张图，环境选择里显示了说明。应用端只跑了一次不用环境；应用里的取用询问和终端对话的界面没有做实机操作。没有做新旧对比实验：默认行为遵循"由模型决定何时看"的设计决定。未运行完整测试套件。
## 0.79.2（尚未发布）

Windows 终端聊天在窗口宽度改变后，先根据控制台的折行结果修正光标位置，再清理或刷新输入区，避免反复缩窄和拉宽后分隔线残留、堆积。修复保留原有布局和聊天记录，不清空整个可见区域。回归使用 Windows ConPTY 中的真实 Chat 界面，覆盖输入草稿、聊天记录保留、高度变化和快速连续缩放，无需模型调用。

## 0.79.1（尚未发布）

新客户端不再把新任务静默交给运行不同代码的忙碌宿主。已有会话仍可查看和结束；旧宿主空闲后会被替换，启动锁内发现的宿主也会核对版本，避免升级后绕过首次选择。Ctrl+O 改为打开临时程序详情视图，再按 Ctrl+O 或 Esc 返回折叠聊天，不再把展开内容永久留在终端历史中。正在运行的程序详情持续刷新，查看期间的新聊天输出会保留并在返回后显示。

## 0.79.0（尚未发布）

Computer 0.6.0 在首次涉及时要求明确选择工作方式、真实键鼠权限、其他窗口信息和屏幕录像。TUI 与交互式 run 命令在启动任务前询问，仅保存明确回答；取消则不启动任务。已有配置和本次任务显式参数继续生效。非交互客户端收到结构化 `choice_required` 响应，子任务申请工作区也检查相同选择。项目目录任务和按需自动安装策略不变。专项检查覆盖未选及无效值、取消、持久化、任务参数覆盖、HTTP 传输和子任务申请。

## 0.78.3（尚未发布）

运行 `harness` 或 `harness chat` 现在会打开新的终端 UI 对话，而不是可选 agent 包的纯文本提示符。第一条消息通过现有宿主启动任务，保留任务选项和附件；打开并关闭空白聊天不会启动任务。专项回归检查复现了原有入口错误，并覆盖两个命令、首条消息选项、模型选择、正常退出和输入输出重定向。

## 0.78.2（尚未发布）

安装新包时，先启用已安装包的模块，再加载其 host 扩展。任务宿主先解析数据目录的实际路径，再创建运行路径，覆盖 macOS 临时目录和符号链接。Computer 0.5.25 不再请求已移除的可选 `chat` 技能，浏览器和桌面任务无需应用前端即可完成配置。新增回归检查在修复前复现了安装、路径和技能错误；macOS 上的 45 项相关检查现已通过。在源码目录外安装 wheel 后，使用 DeepSeek V4.1 Flash 验证了包安装、真实浏览器任务，以及交互聊天中的项目修复。此次本地验证使用本机包仓库，公开仓库尚未更新。未运行全量测试。

终端恢复检查忽略 Darwin 内核自动管理的 `PENDIN` 标记；仅用标准库切换原始输入模式再恢复，也会产生该标记。所有可配置的终端属性仍会逐项比较。

## 0.78.1（尚未发布）

OpenRouter 模型请求现在通过 `HTTP-Referer: https://harness.lmms-lab.com/` 和 `X-OpenRouter-Title: the-harness` 标识应用归属。流式、非流式请求均携带这两个头，覆盖显式 OpenRouter 中转及直连官方域名的兼容客户端；其他提供商保持原有请求头。HTTP 接收端专项检查覆盖取消路径与提供商边界；从独立环境安装 wheel 后，使用 DeepSeek V4.1 Flash 完成两次真实调用，验证实际出站头和成功响应。未运行全量测试。

## 0.78.0（尚未发布）

安装 core 不预选外部产品；任务所需包仍默认自动安装。用户显式配置的 MCP 可通过 stdio 或 HTTP 使用，无需 app 或持久 agent。自定义连接在派发前复核当前授权，排队期间的撤权也对运行中任务生效。任务保留完整 MCP 结果，串行化共享资源，拒绝过期派发并记录迟到回执。MCP 任务入口接受已安装的 workspace 类型、显式目录和任务预算。传输、包管理及任务入口的专项检查覆盖这些契约；真实任务验收在 PR 交付前单独记录。

`harness --version` 输出已安装的 core 版本并退出。

## 0.77.0（尚未发布）

可选前端命令由包提供，core CLI 保持独立。包通过 SDK 调用 core，源码和归档采用明确边界。包管理、workspace 和 agent 专项检查已通过；正式发布仍待确认。

在 macOS 上，`pid_alive` 不再把已经退出、但父进程还没回收的进程（僵尸进程）算作在运行：macOS 没有 `/proc`，现在用 `sysctl` 读取进程状态。运行存活判断、computer 的协调和虚拟机，以及启动锁都依赖它。
